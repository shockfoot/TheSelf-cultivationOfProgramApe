TCP和UDP的区别

|      | UDP | TCP |
| :-- | :---- | :---- |
| 是否连接 | 无连接 | 面向连接 |
| 是否可靠 | 不可靠传输，不使用流量控制和拥塞控制 | 可靠传输，使用流量控制和拥塞控制 |
| 连接对象个数 | 支持一对一、一对多、多对一和多对多交互通信 | 只支持一对一通信 |
| 传输方式 | 面向报文 | 面向字节流 |
| 首部开销| 首部开销小，仅8字节 | 首部最小20字节，最大60字节 |
| 适用场景 | 适用于实时应用（IP电话、视频会议、直播等） | 适用于要求可靠传输的应用，例如文件传输 |

报文：网络中交换与传输的数据单元。报文包含了将要发送的完整的数据信息，其长短不一。

字节流：字节流由字节构成的数据。

UDP报头包括16位源端口号、16位目的端口号、16位UDP长度和16位UDP校验和，共64位即8字节。

TCP报头包括16位源端口号、16位目的端口号、32位序列号、32位确认号、4位头部长度、6位保留位、6位（URG、ACK、PSH、RST、SYN、FIN）、16位窗口尺寸、16位TCP校验和、16位紧急指针共20字节，后可以附带32位选项。

### TCP三次握手

**三次握手**（Three-way Handshake）是指在建立一个TCP连接时，客户端和服务器会一共发送三个报文段。

1. 第一次握手，Client向Server发送一个SYN报文段，报文段的首部中的标志位SYN置为1，另外还会指明自己的初始化序号seq=x，此时客户端处于SYN_SENT状态。
2. 第二次握手，Server收到SYN的报文段后，会以自己的SYN-ACK报文进行应答。该应答报文的首部有三个重要信息：首先SYN被置为1；其次，确认号字段ack=x+1；最后服务器选择自己的初始序号seq=y，表明Server收到了Client发起建立连接的请求并同意建立该连接，此时服务器处于SYN_RCVD状态。
3. 第三次握手，Client收到SYN-ACK报文后，会发送一个ACK报文段，该报文段中序号seq=x+1，确认号ack=y+1，表明Client已经收到Server的确认，此时客户端处于ESTABLISHED状态。服务器收到ACK报文之后，也处于ESTABLISHED状态。此时，双方以建立起了链接。

**第一次握手和第二次握手都只是消耗掉一个序号，但不能携带数据；第三次握手可以携带数据**。

通过第一次握手，Server可以确定Client发送功能正常，服务器接收功能正常，但Client不能确定与Server的单向连接，更加不能确定Server与Client的单向连接。

通过第二次握手，Client发送和接收功能都正常，Server的发送接收功能也都正常，Client可以确定与Server的单向连接，但Server不能确定与Client的单向连接。

通过第三次握手，Client与Server才能确认双方的接受能力、发送能力是否正常，互相确定双向连接，指定自己的初始化序列号，为后面的可靠传送做准备。

### 四次挥手。

四次挥手也就是客户端与服务器断开连接时，需要一共发送四个报文段来完成断开TCP连接。假如客户端发起断开连接的请求（服务器也可以发起），四次挥手过程如下：

1. 第一次挥手：Client发送一个FIN报文段，报文段中指定序号seq=u。此时Client处于FIN_WAIT_1状态。
2. 第二次挥手：Server收到FIN报文后，立即发送一个ACK报文段，确认号为ack=u+1，序号设为seq=v。表明已经收到了Client的报文。此时服务器处于CLOSE_WAIT状态。在第二次挥手和第三次挥手之间的时间段内，由于只是半关闭的状态，数据还是可以从服务器传送到客户端的。
3. 第三次挥手：如果数据传送完毕，Server也想断开连接，那么就发送一个FIN报文，并**重新**指定一个序号seq=w，确认号还是ack=u+1，表明可以断开连接。
4. 第四次挥手：Client收到报文后，一样发出一个ACK报文段做出应答，上一次Client发送的报文段序号为u，那么这次序号就是seq=u+1，确认号为ack=w+1。此时Client处于TIME_WAIT状态，需要经过一段时间确保Server收到应答报文后，才会进入CLOSED状态。Server收到ACK报文后，就关闭连接，也处于CLOSED状态了。

**问题1**：为什么要三次握手？

三次握手是确认双方的能力、发送能力是否正常，指定自己的初始化序列号，为后面的可靠传送做准备。通过第一次握手，Server可以确定Client发送功能正常，服务器接收功能正常，但Client不能确定与Server的单向连接，更加不能确定Server与Client的单向连接。通过第二次握手，Client发送和接收功能都正常，Server的发送接收功能也都正常，Client可以确定与Server的单向连接，但Server不能确定与Client的单向连接。通过第三次握手，Client与Server才能确认双方的接受能力、发送能力是否正常，互相确定双向连接，指定自己的初始化序列号，为后面的可靠传送做准备。只有前两次握手的话，**服务器就不能确认自己回复的报文段是否被客户端接收到，也就不知道自己的发送功能和客户端的接收功能是否正常**。

**问题2**：为什么要四次挥手（中间两个步骤为什么不能合并）？为什么不能直接CLOSE，必须先TIME_WAIT（等待2MSL）？

**ACK和FIN的触发时机是不一样的**。服务器在收到FIN报文后可以立即发送ACK报文，表明服务器收到了客户端的报文；但是服务器想发送FIN报文就需要等到处理完接收缓冲区的数据后才可以第三次挥手，然后等待客户端的第四次挥手ACK。所以挥手需要四次。

报文段最大生存时间MSL（Maximum Segment Lifetime）是任何报文段被丢弃前在网络内的最长时间，超过这个时间报文将被丢弃。理论上，四个报文都发送完毕就可以直接进入CLOSE状态了，但可能网络是不可靠的，有可能最后一个ACK丢失，所以TIME_WAIT状态（等待2MSL）就是用来为了确保服务器收到了最后一段ACK报文。

**如果服务器没有收到最后一段ACK报文**，就会触发超时重传：服务器会再次发送FIN ACK报文。那么在2MSL的时间内，客户端会再次收到FIN报文，客户端就知道刚刚发送的ACK丢失，需要再次发送。**如果服务器收到了最后一段ACK报文**，客户端在2MSL的时间内就不会收到任何报文，客户端就知道刚刚发送的ACK报文没有丢失，不需要再次发送，可以安心进入CLOSED状态了。

**问题3**：什么是进程、线程？什么是线程争用？如何解决？

进程是资源分配的最小单位，线程是CPU调度的最小单位。进程包含线程，线程在进程中运行。一个进程可以包含多个线程。

因为进程中可存在多个线程，线程间均可访问主线程资源。所以若线程间争抢资源，可能导致数据混乱。

只要保证避免同一时间只有一个线程来访问共享数据即可。可以使用Monitor和Lock实现。

**问题4**：线程和协程的区别

|      | 协程（Coroutine） | 线程（Thread） |
| :---- | :----------------- | :-------------- |
| 是否允许并发 | 否 | 是 |
| 是否运行在子线程 | 否 | 是 |
| 是否存在线程争用问题 | 否 | 是 |
| 是否允许访问UnityAPI | 是 | 否 |

**问题5**：CPU同一时间只能执行一个线程，为什么存在并发问题？

CPU切换线程并不会管线程是否将代码执行完毕，而是和分给线程的时间片是否到期有关，时间片到期了就会切换线程，并发问题也就因此产生了。

## ScoketTCP网络架构需求与设计

### 需求分析

设计一个安全稳定的网络架构，需求是这样的：

- 双侧通讯：Lua侧和C#侧都有网络通讯的需求，希望都能支持
- 数据安全：希望能在设计中，增加协议保护
- 黏包拆包：通讯数据可能出现黏连，希望能正确解析
- 心跳包：服务器怎么知道客户端“在不在线”
- 断线重连：客户端“断线”时，用户能无感知的连接上服务器，提升用户体验
- 客户端“丢包”：在通讯过程中，客户端“断线”，希望服务器没处理成功的C2S，可以再处理一遍

黏包：当发送端缓冲区的长度大于网卡的MTU时，TCP会将这次发送的数据拆成几个数据包发送出去。 如果本机的MTU比网关的MTU大，大的数据包就会被拆开来传送，这样会产生很多数据包碎片，增加丢包率，降低网络速度。TCP的协议数据不会丢，没有收完包，下次接收，会继续上次继续接收，己端总是在收到ack时才会清除缓冲区内容。数据是可靠的，但是会粘包。

MTU是Maximum Transmission Unit的缩写，意思是网络上传送的最大数据包。MTU的单位是字节。大部分网络设备的MTU都是1500。

解决黏包：

1. 首先将所有接收到的字节流，塞入缓冲池；
2. 根据包头信息，判断是否能获取当前完整协议包。若能获取完整，则根据协议头提取数据。此时若有缓冲池还有其他协议数据，若能继续提取就继续，不能则跳过，继续等待接收新字节流，塞入缓冲池；
3. 循环1和2。

实现心跳包：指定间隔时间内（比如5秒）， 定时向服务器发送一条指定的心跳协议。

断线重连触发时机：Socket Connect时，超时或异常；Socket Receive/Send时，异常；客户端“丢包”时，指定时间内收不到回包；Summary校验码客户端服务器不一致等。

TCP是可靠通信，那为什么会 “丢包” 呢？

在客户端断线时，可能发送了一些本地的消息协议出去，但是因为客户端断线了，服务器没收到，导致认为“丢包”了。

解决：协议数据重发。C2S发送出去，务必返回对应的S2C协议；S2C协议作为Key，C2S作为Value，存储在字典容器中；收到对应的S2C后，移除该值；若未收到，则游戏界面转圈，等待一定时长后，启动断线重连，此时，将这个字典内现有的协议，再重新发送一次。注：排除掉心跳包，因为收发太频繁。
